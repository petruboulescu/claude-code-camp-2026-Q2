# 01 · Struct Skeleton (Python)

Python port of `week1_baseline/ruby/01_struct_skeleton`. This step keeps the
configuration layer from `00_config` and adds the first runtime data
structures that the agent loop will pass around constantly:

- `boukensha.Tool`
- `boukensha.Message`
- `boukensha.Context`

The goal here is still iterative. We are not adding API calls or tool
execution yet. We are only shaping the objects that later steps will use.

## Design

Ruby uses lightweight `Struct`s for `Tool` and `Message`, plus a small mutable
`Context` class. The Python port follows the same intent:

- `Tool` is a frozen dataclass holding metadata plus a stored callable
- `Message` is a frozen dataclass representing one conversational turn
- `Context` is a mutable class holding task, system prompt, message history,
  and registered tools

`Config`, `Task`, and `PLAYER` are carried forward from `00_config` without
changing their behavior.

## Data Structures

### `Tool`

Represents a callable tool the agent is allowed to use.

| Field | Description |
|------|-------------|
| `name` | The name of the tool |
| `description` | Shown to the agent so it knows when to invoke the tool |
| `parameters` | The arguments that need to be passed in |
| `func` | The actual Python callable that runs when the tool is called |

### `Message`

A single unit of conversation between the user and the agent.

| Field | Description |
|------|-------------|
| `role` | Who is speaking: user, assistant, or tool_result |
| `content` | The text generated by the agent or provided by the user |
| `tool_use_id` | Optional ID linking a tool result back to the tool call |

### `Context`

Holds everything the runtime needs to make an eventual model call.

| Field | Description |
|------|-------------|
| `task` | The task object driving this context |
| `system` | The resolved system prompt |
| `messages` | The conversation history |
| `tools` | The registered tools keyed by tool name |

Helper methods:

- `register_tool(tool)` stores the tool by name
- `add_message(role, content, tool_use_id=None)` appends a message
- `tool_count` reports how many tools are registered
- `turn_count` reports how many messages exist

## Setup

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r week1_baseline/python/01_struct_skeleton/requirements.txt
```

## Run Example

With the venv active:

```bash
./week1_baseline/python/bin/01_struct_skeleton
```

Expected output shape:

```text
=== Boukensha Step 1: Struct Skeleton ===

Config:   <boukensha.Config dir=... tasks=player>
Context:  <Context task=player turns=2 tools=1>
Tool:     <Tool name=move description=Move the player ... params=['direction']>
Messages:
  <Message role=user content=Explore north and tell me what you find....>
  <Message role=assistant content=Sure, let me head north and take a look....>
```

## Notes

- `Tool.func` is stored but not executed in this step's example.
- `Context` does not yet serialize into any provider-specific API format.
- Prompt resolution and config loading still behave exactly like `00_config`.
